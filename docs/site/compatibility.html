What compatibility means here

This page separates code paths that are verified by the repository from integrations that are supported with configuration or best effort. A compatibility label does not promise that every theme, plugin, host, or extension can share one request unchanged.

Verified, supported, best effort, and known limitation

  • Verified: exercised by the current automated checks or a recorded live smoke test.
  • Supported: an implemented path with documented configuration and recovery.
  • Best effort: implemented for common setups, but site-specific testing is required.
  • Known limitation: a deliberate boundary where the feature cannot promise a universal result.

How to test a compatibility change

  1. Record WordPress, PHP, server, theme, page builder, WooCommerce, Redis, and CDN versions.
  2. Run wp wppo verify and wp wppo system-info.
  3. Test a logged-out page, a logged-in page, the block editor, navigation, and the main form.
  4. Test cart and checkout when WooCommerce is active.
  5. Purge one URL and inspect the origin and edge response headers.
  6. Keep a redacted copy of the result. Never include passwords, API keys, cookies, or authorization headers.

When a builder or extension conflicts

Start with the narrowest safe control. Keep the page cache, builder preview exclusion, delayed-script exclusion, or CSS safelist in place while the failing feature is off. Re-test after the builder regenerates assets.

FAQ

Does supported mean every extension works?

No. It means the plugin has an implemented path and a documented boundary. Test the exact stack.

Can I use two cache plugins?

Only with one page-cache owner. Disable the competing page cache and retain the other features only after testing.

How do I report an incompatibility?

Include versions, the exact feature, reproduction URL, and redacted wp wppo system-info output. Full workflow: Support.
