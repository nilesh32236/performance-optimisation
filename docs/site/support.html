Get help without exposing private data

Use this page to make a site safe again, collect useful evidence, and report a reproducible problem. Performance Optimisation does not need your passwords, API keys, cookies, or authorization headers to investigate a performance issue.

Before you report a problem

  1. Record the affected URL and the exact setting or action.
  2. Disable the most recent advanced optimization: Delay JavaScript, Used CSS, Critical CSS, Combine CSS, or CDN edge handling.
  3. Save, clear the affected page cache, and test in a logged-out window.
  4. Run wp wppo verify and wp wppo system-info.
  5. Compare the result with the same URL before the change.

What to include

  • WordPress and PHP versions
  • Server software and cache owner: Apache, nginx, LiteSpeed, or CDN
  • Theme, page builder, WooCommerce, Redis, and CDN versions when relevant
  • Reproduction steps and expected versus actual behavior
  • Redacted output from wp wppo system-info and wp wppo verify
  • Browser console or Network-panel details with secrets removed

What not to include

Do not post passwords, API keys, bearer tokens, cookies, session IDs, private URLs, customer data, or complete database exports. Redact hostnames and identifiers when they are not needed to reproduce the issue.

Where to find evidence

  • Tools: System Info, Activity Log, settings export, and snapshot status.
  • Dashboard: cache size, last clear, image status, recent activity, and guided next step.
  • WP-CLI: wp wppo verify, wp wppo system-info, and feature-specific status commands.
  • Browser: response headers, console errors, and the Network panel for the affected URL.

Safe recovery

Use the existing controls: disable the narrow feature, clear the exact page, restore a preset snapshot, or use the setting restore point. If the site remains broken, deactivate the plugin from WordPress and inspect the PHP error log. Do not delete an unknown cache or object-cache drop-in.

Upgrading

Before an upgrade, record the current cache owner, export settings without secrets, and test on staging when possible. After upgrading, run wp wppo verify, inspect the Dashboard notices, and test a logged-out page plus the main form. Existing settings remain in the plugin's settings store; a compatibility change can still require a new staging test.

FAQ

Can support reproduce my site?

Start with a public or staging URL, exact steps, and redacted system information. A support conversation does not require access to your admin account.

Why do you ask for a cache owner?

A stale origin, LiteSpeed, or CDN layer can look like a plugin bug. The owner determines which purge path to test.
