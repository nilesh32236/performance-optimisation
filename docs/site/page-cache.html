What it does

Page Cache saves a rendered HTML response as a static file. On a hit, the owned advanced-cache.php drop-in can serve the file before WordPress boots, avoiding PHP and most database work for that request.

When to use it

Use Page Cache on a public WordPress site with mostly cacheable content. Keep dynamic routes out of it. It is usually the first performance layer to verify when TTFB is high on anonymous requests.

Safe default

enableCache starts enabled for eligible anonymous traffic. Logged-in variants are off by default. WooCommerce safe mode is on. Cart, checkout, account, Store API, AJAX, admin, REST, feeds, unsafe queries, and private responses stay outside shared cache.

How to enable it

  1. Open Dashboard → Page Cache.
  2. Confirm Enable Page Cache is on.
  3. Review the cache lifespan and post-type overrides.
  4. Save, clear the affected page, and load it in a logged-out window twice.
  5. Run wp wppo cache status.

What changes

Eligible responses are written under wp-content/cache/wppo/ and served as a stored file. Publishing, settings changes, theme or plugin changes, permalink changes, and manual clears can invalidate affected URLs. Derived CSS and edge layers may also be purged.

Compatibility considerations

  • WooCommerce safe mode protects dynamic routes and session cookies.
  • LiteSpeed has explicit coexistence modes. Keep one page-cache owner.
  • Logins, REST, feeds, error pages, and unsafe query strings intentionally miss.
  • Another plugin can set DONOTCACHEPAGE or use the documented request filter. Known unsafe Woo routes remain fail-closed.

How to verify

wp wppo cache status
curl -sI https://example.com/ | grep -iE 'etag|last-modified|vary|x-litespeed-cache'
wp wppo cache clear --page=/sample-page/

Check the first miss and second hit, response validators, cache directory, and page count. A smaller response is not enough if the content is stale or wrong.

How to undo or disable

Turn off Enable Page Cache, save, and clear the cache. Use Restore or the automatic settings restore point when a preset changed the value. The plugin-owned drop-in is removed during the controlled deactivate/uninstall path, not by deleting arbitrary files.

Troubleshooting

  • Nothing is cached: check enableCache, WP_CACHE, the owned drop-in, directory permissions, and request gates.
  • Stale content: publish a test change, inspect invalidation, then clear the exact URL and derived CSS.
  • Woo cart issue: turn WooCommerce safe mode on, save, clear cache, and run the Woo self-test.
  • Cache is growing too fast: review size and file-count caps before increasing them.

FAQ

Does Page Cache cache my admin?

No. Admin and authenticated requests are excluded unless a narrow, explicit path allows otherwise.

Why does the second request look faster?

The second request can reuse a stored HTML file instead of rendering WordPress again.

Can I run it beside LiteSpeed Cache?

Use the LiteSpeed coexistence mode that names the page-cache owner. Do not let two orchestrators write the same URL.
