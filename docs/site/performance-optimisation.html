Performance Optimisation is a WordPress performance plugin for teams that want measurable improvements without a stack of overlapping optimizers. The current release is 2.4.0 and requires WordPress 6.2+ with PHP 8.2+.

The plugin combines a static HTML cache, optional Redis object caching, asset and image delivery controls, database cleanup, PageSpeed Insights, first-party Web Vitals, and compatibility adapters for LiteSpeed and WooCommerce. The dashboard exposes seven working areas: Dashboard, File Optimisation, Preload, Image Optimisation, Database, Object Cache, and Tools.

Request layers

A request can pass through several layers. Each layer is optional or conditional, and the plugin never silently replaces a foreign cache drop-in.

  1. Edge CDN — Cloudflare, Bunny, Varnish, or a configured CDN mapping can serve and purge assets or HTML.
  2. Server cache — LiteSpeed/OpenLiteSpeed can own responses through the coexistence adapter; Apache and nginx use generated server rules where applicable.
  3. Static page cache — complete HTML files under wp-content/cache/wppo/, served by the owned advanced-cache.php drop-in before WordPress boots.
  4. Redis object cache — an optional object-cache.php drop-in for repeated database reads and transients.
  5. PHP and WordPress — the normal request path, where asset, image, CSS, preload, and monitoring policies run.

Start with your task

  • Improve Core Web Vitals — begin with LCP, INP, or CLS evidence.
  • Enable Page Cache — verify one anonymous miss and hit.
  • Optimize images — protect the LCP hero before enabling broad lazy loading.
  • Improve LCP with Preload — add one measured resource hint.
  • Check compatibility — read the verified and known-limitation boundaries first.

First run

  1. Read Installation and verify filesystem and server requirements.
  2. Open the Dashboard and confirm the detected server, cache status, and diagnostics.
  3. Keep the default cache and native lazy-loading behavior while you test one optional feature at a time.
  4. Enable CSS/HTML/JavaScript changes, then images, preload, Redis, or edge integrations only after each change is verified.
  5. Run wp wppo verify and compare a fresh PageSpeed or field-data baseline with your own traffic.
