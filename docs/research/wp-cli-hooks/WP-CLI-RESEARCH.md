**Date:** 2026-08-28 · **Plugin:** `performance-optimisation` v1.9.0  
**Scope:** WP-CLI official handbook, command cookbook, argument syntax, internal API, built-in commands, and mature plugin CLIs vs `includes/class-wppo-cli-command.php:1-973` (7 subcommands, `wp wppo`, `@since 1.9.0`, registered at `includes/class-main.php:472-474`).  
**Method:** Read `class-wppo-cli-command.php` + `class-main.php:436-475` fully; WebFetch/WebSearch handbook + 5 plugin CLIs. Prioritise `make.wordpress.org/cli` and `developer.wordpress.org/cli`. Research-only.

## 0. Summary Verdict

| Dimension | Official convention | WPPO (`wp wppo`) | Gap |
|-----------|---------------------|-------------------|-----|
| **Namespace** | `wp <package> <noun> <verb>` or `wp <ns> <subcommand>` via `WP_CLI::add_command('wppo', Class)` | `wp wppo {cache,database,image,settings,object-cache,pagespeed,system-info}` — matches | OK |
| **Help** | Docblock `## OPTIONS` + `## EXAMPLES` parsed → synopsis (`<pos>` / `[--assoc=<val>]` / `[--flag]`), `@subcommand` for dashes/reserved, `@when after_wp_load` | All 7 have `## OPTIONS` + `## EXAMPLES` + `@when after_wp_load` + `@subcommand` (object-cache/system-info need it). Positional defaults done in code (`$args[0] ?? 'clear'`) not synopsis-enforced | Synopses use `<action>` optional-but-described-as-required; should be `[<action>]` |
| **Args** | Positional `<required>` vs `[<optional>]` vs `[<opt>...]`; assoc `[--key=<val>]` vs `[--flag]` vs `[--field[=<val>]]`; `---` YAML for defaults/options | Uses positional `<action>` + assoc `--type/--page/--tables/--format/--file/--settings/--host…` correctly, but `<action>` marked required when code treats it optional | Fix synopsis brackets |

| **Exit codes** | `WP_CLI::success` → stdout `Success:` exit 0; `WP_CLI::error($msg, true)` → stderr `Error:` exit 1; `WP_CLI::warning` → stderr continue exit 0; `WP_CLI::halt($code)` for script-testing | Uses all three correctly; one inconsistency: `pagespeed results` absence → `warning` exit 0 vs `error` exit 1 (handbook: binary `is-installed` uses exit 1 for “not found”) | Decide policy |
| **Output modes** | `WP_CLI\Utils\format_items($format, $items, $fields)` + `Formatter` → `table|json|csv|yaml|count|ids|ids` + `--field=<f>` / `--fields=<list>` | Only `settings get --format=json|yaml` uses format; others hardcode `wp_json_encode(PRETTY)` + `WP_CLI::log` | Add `--format` + `format_items` |
| **Progress** | `WP_CLI\Utils\make_progress_bar($msg,$count)` → `tick()/finish()`, auto-disabled when piped | No progress bar anywhere (image 50/batch, database batches, cache walks) | Add for >50-item ops |
| **Dry-run / --yes** | `WP_CLI::confirm($q,$assoc_args)` respects `--yes`; destructive should prompt; `--dry-run` for mutations (e.g. `wp search-replace --dry-run`) | No `confirm`/`--yes`, no `--dry-run` on `database cleanup`, `cache clear`, `object-cache disable`, `settings import` | Add `confirm` + `--dry-run` |
| **--quiet/--verbose** | Global `--quiet` suppresses `log/success` but not `line/error`; `--debug[=<group>]` for verbose | Uses `log/success/warning/error` (quiet-aware) correctly; no `--verbose`/`debug` branches | OK |
| **Batching** | Chunk with `Iterator`, `make_progress_bar`, `clean_post_cache`, `wp_cache_flush` per chunk | Batches exist in service layer (`Database_Cleanup::delete_in_batches 1000`, `image batch 50`, `cache status walk 5000`) but no CLI `--batch-size`/`--limit` flag | Expose batch knob |
| **Multisite** | Global `--url=<url>` selects blog; `--network` for all sites (e.g. `wp user list --network`); `--site_id` where available; `switch_to_blog` loop | No explicit `--url/--network/--blog_id` handling; relies on WP-CLI core `--url`; no `--network` sweep | Document + add network flag |
| **Performance** | Bootstrap cost dominates; use `when => before_wp_load` only for non-WP commands; `after_wp_load` for WP-dependent | All `@when after_wp_load` (correct — plugin-loaded command, handbook notes `@when` ignored for plugin/theme commands) | OK |
| **Bootstrap** | Plugin/theme: `if (defined('WP_CLI')&&WP_CLI) WP_CLI::add_command(...)` in `includes()` after vendor autoload; PSR-4 optional | `class-main.php:472-474` inside `Main::includes()` after `vendor/autoload.php` + `action-scheduler.php` — matches handbook `Include in a plugin or theme` | OK |

**Comparison — WPPO naming:**

- `WP_CLI::add_command('wppo', 'PerformanceOptimise\Inc\WPPO_CLI_Command')` at `class-main.php:472-474` — correct, unconditional handbook pattern “Include in a plugin or theme: conditionally load based on presence of WP_CLI constant” (https://make.wordpress.org/cli/handbook/guides/commands-cookbook/#include-in-a-plugin-or-theme). Guard `if (defined('WP_CLI') && WP_CLI)` present.
- Depth 2 (`wppo <subcommand>`) with positional `<action>` third token (`cache clear`, `database cleanup`) — equivalent to `wp plugin install` depth 2 and `wp litespeed-purge post_id 1 3 5` depth 2. Acceptable, though handbook prefers `wp wppo cache-clear` style not used; our `<action>` switch is idiomatic (Rocket uses `clean` vs separate `purge` verbs).
- Convention win: keep `wppo` short; consider alias `wp performance-optimisation`? No — `wppo` is discoverable via `wp help wppo`.
- Issue: no `wp wppo --help` class verbs listed in docs beyond `cache/database/image/settings/object-cache/pagespeed/system-info` (7) — missing siblings that SPA has (`rum`, `ai`, `litespeed`, `llms`, `edge`) — not a naming bug but coverage gap (see WP-CLI-CURRENT §5).

**WPPO gap — synopsis required vs optional:**

Handbook: `<action>` means **required** positional; `[<action>]` means optional. WPPO docblocks say `## OPTIONS\n\n<action>\n: Cache action…` (`:49-51`) indicating required, but code does `$action = $args[0] ?? 'clear'` (`:76`) defaulting. Same for `database` (`:131` `<action>` but code `$args[0] ?? 'cleanup'` `:175`), `image` (`:301` `<action>` but code `?? 'status'` `:322`), `object_cache` (`:757` `<action>` but `?? 'status'` `:802`), `pagespeed` (`:880` `<action>` but `?? 'scan'` `:903`). Handbook convention would mark these `[<action>]` since they have defaults. Fix: change docblocks to `[<action>]` or `* Call without argument defaults to …` note; otherwise `wp help wppo cache` misstates required.

Also `system-info` correctly uses `[<group>]` (`:938`) matching optional code `?? null` (`:958`).

**Comparison — WPPO arg handling:**

- Positional defaults exist but not declared in synopsis (see §2 gap).
- Assoc validation via code allowlists (`database` TABLE_MAP `:180`, `image` format `webp|avif|both` `:335-337`, `object-cache` 6-key allowlist `864-871`, `settings` `ALLOWED_SETTINGS_KEYS` `644`) — correct per Woo/LSCWP pattern but handbook prefers synopsis `options:` to let WP-CLI validate before invoke (early error message).
- No `[--flag]` boolean flags (only value-assoc) — missing `--dry-run`, `--yes`, `--confirm`, `--verbose` that handbook cookbook expects for destructive/migratory commands.
- No variadic `...` — could be used for `wp wppo database cleanup revisions trashed_posts …` but current `--type=all` is cleaner.
- File arg `[--file=<path>]` handled via `WP_Filesystem` existence check (`:603-607,:629-632`) — aligns with `wp user import-csv <file>` pattern at `developer.wordpress.org/cli/commands/user/import-csv/` which validates `file_exists`. Good.
